持有证明（Proof-of-Possession）登录 · P-256 挑战签名

浏览器用 Web Crypto 生成 不可导出 的 ECDSA P-256 私钥并存入 IndexedDB（同源标签页共用）；登录时提交公钥并绑定新会话。 /api/me、/api/logout 必须先领取 60 秒随机挑战，再提交覆盖「挑战 + HTTP 方法 + 路径」的 ECDSA-SHA256 签名。 只复制 Cookie、重放签名都会被拒；同一挑战并发重放仅一次成功。原有的密码猜测限额、并行核验与断连结算保持不变。

演示 A：复制 Cookie 到另一浏览器 无密钥 → 拒绝

先登录，然后点按钮经签名接口取回当前 Cookie 值（HttpOnly，JS 读不到，故由服务端在签名校验后返回）， 把它粘贴到下方「无密钥客户端」——该上下文故意不持有 IndexedDB 私钥，模拟只偷到 Cookie 的攻击者。

演示 B：同挑战并发重放 仅一次成功

先登录。点按钮领取 一个 挑战并生成 一份 有效签名，然后把同一个（挑战, 签名）对 同时并发提交 N 次到 /api/me：服务端原子消费，预期恰好 1 个 200，其余全部 401。

建议演示步骤与安全语义

  1. 页面加载即生成不可导出 P-256 私钥（IndexedDB）；刷新、新开同源标签页共用同一密钥。点「重新生成密钥」后旧会话签名将失效，需重新登录绑定新公钥。
  2. 用 alice 登录：请求体带公钥，成功后会话行绑定该公钥。点「刷新身份」可观察两次请求：先 POST /api/challenge 领 60 秒挑战，再 GET /api/me 并在 X-Auth-Challenge / X-Auth-Signature 头里提交 ECDSA 签名。
  3. 演示 A：取回 Cookie → 在无密钥客户端点 GET /api/me（仅 Cookie，401）；尝试领挑战后用空/伪造签名调用也 401。把 Cookie 粘到另一个浏览器的开发者工具里同样无法通过。
  4. 演示 B：同一挑战+签名并发 8 份，结果恰有 1 个 200、7 个 401（挑战已消费）；两个 Web 进程共享 SQLite，原子事务保证跨进程也只成功一次。
  5. 多标签页各自领挑战互不覆盖；挑战绑定会话与用途（me 挑战不能用于 logout，反之亦然），签名覆盖方法与路径，跨端点重放被拒。
  6. 验签失败 不消费 挑战，60 秒内可用正确签名重试；挑战过期或会话注销后迟到的签名不再有效，注销不能被迟到验签恢复。
  7. 密码限额演示保持原样：6 并发错误密码第 6 个立即 429、断连后服务端仍结算；docker compose restart 后会话与未过期挑战保留，旧版未绑定公钥的会话一律拒绝。
